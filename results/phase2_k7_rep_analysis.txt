Kernel 7 — memcpy_rep (size-gated `rep movsb`) — analysis
=========================================================

Rung
----
src/memcpy_rep.c: for n >= 256 B one `rep movsb` for the whole copy; below the
gate, kernel 2's word loop (8 B via __builtin_memcpy + byte tail). The gate was
chosen before the measurement from the start-up cost of `rep movsb` on a core
without ERMS/FSRM (tens of cycles) versus 256 B at ~32 B/cycle: below that, the
start-up alone is the copy.

Verify -- PASS on znver2, znver3, v3 (glibc reference, n = 0..4096 at random
offsets, 64 B canaries both sides, plus the ladder sizes). Gate -- audit and
audit-width PASS.

Codegen (build/znver2/src/memcpy_rep.o), the whole kernel:

    cmp    $0xff,%rdx
    jbe    word_loop
    mov    %rax,%rdi ; mov %rdx,%rcx
    rep movsb (%rsi),(%rdi)
    ret
    word_loop: 8 B load/store loop + byte tail

No vector instructions (the TU is in SCALAR_SRCS and the audit enforces that).

rep vs naive (the same byte-at-a-time baseline the ladder started from)
----------------------------------------------------------------------
rep is faster than `naive` at every size, by +47.7% at 16 B to +95.6% at 4 KB
(certified, Tier A). That is the only comparison it wins, and it is the one that
says what `rep movsb` is worth here: better than a byte loop, worse than every
kernel with a vector unit.

What this means
---------------
The Phase 0 finding — no ERMS, no FSRM — is confirmed behaviourally. `rep movsb`
on this core costs a fixed start-up of tens of cycles and then copies in
microcode:

  - fixed cost dominates below ~4 KB. At 256 B it is 21.5 ns for what glibc does
    in 3.7 ns (5.8x). The cost is not separable into a clean start-up plus a
    per-byte rate from these points — 256 B is 21.5 ns but 512 B is only 23.8 ns,
    so the 128→256 step (+8.7 ns) costs more than the 256→512 step (+2.3 ns),
    which is a property of the microcoded path for those counts, not of a linear
    model. What can be said without a model: at every size below 4 KB the rung is
    1.4x to 5.8x behind, so no setting of the gate inside that range could have
    rescued the class.
  - the gap narrows as the size grows and reaches its minimum at 64 KB
    (-1.60%, i.e. 1.6% behind glibc), which is where the per-byte rate finally
    amortises the start-up.
  - above 64 KB it widens again — 256 KiB is 2.0x behind, 1 MiB is 2.7x behind,
    4 MiB is 2.3x behind — because glibc is using non-temporal stores and a
    4 KB-ahead prefetch stream there while `rep movsb` keeps allocating in cache.

Verdict
-------
REJECTED, as predicted, and kept as ladder evidence. No size at which this rung
is competitive with the vector rungs exists on this host; the rung's value is
that it converts "no ERMS" from a CPUID reading into a measured curve, and it
puts a number on what the ERMS-less penalty costs (up to 5.8x at 256 B).

Limitations
-----------
  - The gated word loop is kernel 2's, so the sub-256 B rows measure that loop,
    not `rep movsb`. Both are reported; the gate is at 256 B and the table says
    which side each size falls on.
  - This host is a 4-vCPU KVM guest on shared silicon; the 4 MiB rows are Tier B
    and are not claims. Nothing above depends on them.
